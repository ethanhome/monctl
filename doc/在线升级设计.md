# monctl 在线升级设计

本文档是 `/grilling` 访谈的结论汇总。目标、约束、交互、平台细节和验收矩阵都在这里;实现时不再另行发挥。

## 1. 目标

把"去 GitHub Release 手动下载 → 安装 → 清理旧版本"替换为:

- **GUI**:启动后静默检查,有新版在界面内提示,用户点一下完成下载、校验、替换、重启。
- **CLI**:`monctl upgrade` 手动触发,命令行内确认后原地替换。

两者共用 `internal/update` 的检查、下载、校验、替换逻辑;CLI 只是多一个入口,不维护第二条实现路径。

## 2. 范围

| 项 | 决定 |
|---|---|
| 平台 | Windows amd64、macOS arm64(与现有发布目标一致) |
| 更新通道 | 仅 stable;GitHub `releases/latest`(自动跳过 prerelease) |
| `dev` 构建 | 不检查、不升级;`monctl upgrade` 明确提示"开发版不检查更新" |
| 更新源 | GitHub API `releases/latest` + release 内 `SHA256SUMS` |
| 首次安装 | 不变:`.dmg` / 裸 `.exe` / 裸 CLI 二进制 |

不做:签名与公证、静默全自动安装、版本目录/包管理器语义、beta 通道、启动健康检查崩溃回滚、sudo/UAC 提权、Linux。

## 3. 发布产物

release 在现有 4 个产物之外新增 2 个:

| 文件 | 用途 |
|---|---|
| `monctl-windows-amd64.exe` | CLI,不变 |
| `monctl-gui-windows-amd64.exe` | GUI,不变 |
| `monctl-darwin-arm64` | CLI,不变 |
| `monctl-macos-arm64.dmg` | GUI 首次安装,不变 |
| `monctl-macos-arm64.zip` | **新增**,GUI 更新器专用;zip 根下为 `monctl.app` |
| `SHA256SUMS` | **新增**,覆盖以上 5 个产物 |

`SHA256SUMS` 由 release job 在汇总产物后生成(`sha256sum *`),格式为标准 `<sha256>␣␣<filename>`。zip 由 `ditto -c -k --keepParent` 从 `build/bin/monctl.app` 生成,保留权限与符号链接语义。

## 4. 完整性校验

- 传输:HTTPS。
- 校验和:`SHA256SUMS` 从同一 release 的 asset 获取;目标产物必须**恰好有一条**记录,缺失或不一致即中止。
- macOS 额外校验:解压后 zip 根下必须恰好有一个 `monctl.app`;读取 `Contents/Info.plist` 的 `CFBundleShortVersionString`,必须等于 tag 去掉 `v` 的字符串,否则中止(防产物与 tag 错配)。
- 解压防护:拒绝绝对路径、`..` 路径穿越和符号链接条目;任何条目越出临时目录即中止。
- **不执行**下载的二进制来询问版本。
- 未来可把 SHA256 校验替换为 minisign 验签;当前把校验实现成独立函数即可。

## 5. 安装与替换

### 5.1 macOS(GUI)

1. 用 `os.Executable()` 回溯到当前运行的 `.app` 根目录,**就地替换用户实际运行的那个 bundle**(通常是 `/Applications/monctl.app`,不写死路径)。
2. 以下情况不弹 sudo、不提权:
   - 运行在只读卷(挂载的 dmg、`/private/var/folders/.../AppTranslocation/`)→ 提示"请先把 monctl 拖入 Applications,再使用自动更新",按钮打开 release 页面。
   - 目录不可写 → 提示"没有写入权限",按钮打开 release 页面。
3. 正常时序:下载 zip → 校验 → 解压到**同卷**临时目录 → 校验 `Info.plist` 版本 → 当前 `.app` 改名为 `monctl.app.old` → 新 `.app` `rename` 到位 → 提示重启。
4. 任一步失败 → 把 `.old` 改回原名;原版本必须完好可用。

### 5.2 Windows(GUI)

1. 新 exe 下载到**当前 exe 所在目录**(必须同卷才能 rename)的 `*.new`。
2. 校验 SHA256 → 当前 exe 改名为 `*.old` → `*.new` 改成正式名 → 提示重启。
3. 失败 → `.old` 改回原名。
4. 目标目录不可写 → 降级到"打开 release 页面",不弹 UAC。
5. "立即重启":先启动新实例,再退出当前进程。

### 5.3 CLI

与 GUI 相同的替换机制,作用于 `os.Executable()` 指向的二进制:

- macOS:直接 `rename` 替换。
- Windows:`.exe.new` → 当前 `.old` → `.new` 到位;命令执行完毕进程退出即生效,无需重启。
- 目录不可写:明确报错,不弹 UAC。

### 5.4 `.old` 生命周期

- 替换失败 → 立即恢复,自动回滚。
- 替换成功后,`.old` **不在新版本首次启动时删除**;GUI 与 CLI 每次启动时清理**存在超过 24 小时**的 `.old`(best-effort,失败忽略)。
- 不做"启动健康检查后自动回滚";新版本若无法启动,给用户一天时间手动恢复。README 提供手动恢复命令。
- 不提供"恢复上一版本"UI(新版本启动不了时 UI 也打不开)。

## 6. 更新源与网络

- `GET https://api.github.com/repos/ethanhome/monctl/releases/latest`,超时 10 秒,带 `User-Agent`。
- 尊重 `HTTPS_PROXY` 等标准代理环境变量(Go 默认 Transport 即可)。
- 下载同样 10 秒连接超时,整体不设硬性总时长(大 dmg/zip 可能慢),但支持取消。
- 未认证 API 限流 60 次/小时;GUI 有 24h 节流,CLI 每次手动触发,不额外处理限流,失败按错误呈现。

## 7. 交互

### 7.1 GUI

- 启动后延迟约 5 秒静默检查;自动检查失败(网络、限流、超时)完全静默。
- 24 小时内不重复请求,节流时间持久化在设置文件。
- 提示形态:不使用独立提示条,更新状态全部体现在 footer 的 `更新` 按钮上。
  - **无新版**:`更新` 置灰禁用。
  - **可更新**:`更新` 点亮(主色),点击开始应用内升级。
  - **进行中**:按钮文案显示"下载中…"/"安装中…"并禁用;再次点击"检查更新"被忽略。
  - **完成**:按钮变为"重启以完成更新",点击重启。
  - **失败**:按钮变为"打开下载页",toast 显示原因;不自动重试,用户可再点。
- 底部新增 footer:左侧 `monctl v0.3.0`,右侧 `检查更新`、`更新` 与 `设置` 三个文字按钮。
- `设置` 打开轻量对话框(复用现有 dialog 样式),当前只有"启动时检查更新"复选框。
- 手动 `检查更新`:绕过 24h 节流,并刷新 `lastUpdateCheck`;有新版点亮 `更新` 按钮,无新版 toast"已是最新版本",出错 toast 显示原因。
- 更新流程与 DDC 扫描/滑块互不阻塞,只在 UI 上并存。

### 7.2 CLI

`monctl upgrade [--check] [--yes]`:

- 默认:检查 → 打印当前版本、最新版本、将替换的文件路径 → 询问 `y/N`。
- `--check`:只检查,不下载。
- `--yes`:跳过确认。
- 非 TTY 且未给 `--yes`:只打印计划并退出,不擅自动手。
- `dev` 构建:报"开发版不检查更新",非零退出。

退出码(与现有 `0/1/2` 习惯兼容):

| 码 | 含义 |
|---|---|
| 0 | 已是最新,或升级成功 |
| 1 | 升级失败 |
| 2 | 参数错误 |
| 10 | `--check` 且发现新版 |
| 11 | `--check` 且检查失败 |

## 8. 设置文件

`internal/settings` 新增两个字段,无版本字段;缺失即默认值:

```json
{
  "disableUpdateCheck": false,
  "lastUpdateCheck": "2026-11-20T12:34:56Z"
}
```

- `disableUpdateCheck` 缺失 = `false` = 启动时检查(默认开启)。用 `disable` 命名是为了让零值自然等于默认行为,不需要 `*bool`。
- `lastUpdateCheck` 为 RFC3339;缺失 = 从未检查。
- `Snapshot()` / `clone()` / 写入路径同步更新。
- CLI 不读写设置文件。

## 9. 代码结构

```
internal/update/
  version.go      版本比较(v* 语义,使用 golang.org/x/mod/semver)
  release.go      release/asset 选择、SHA256SUMS 解析
  checksum.go     SHA256 校验(独立函数,未来可换验签)
  zip.go          zip 安全解包
  checker.go      GitHub API 客户端(10s 超时)
  downloader.go   下载到临时文件
  install.go      Installer 接口 + 通用回滚时序
  install_darwin.go   app bundle 定位、替换、Info.plist 版本读取
  install_windows.go  exe 改名让位
  install_other.go    不支持平台返回明确错误
```

- `Installer` 接口语义:接收"已校验的临时文件/目录",把它装到位;失败时保证原状。
- `cmd/monctl` 增加 `upgrade` 子命令,只做参数解析、交互、输出与退出码。
- `gui/app.go` 增加绑定方法(检查状态、开始更新、重启、读取/保存设置),把进度通过 Wails 事件推给前端;更新状态机放在 `internal/update` 或一个薄封装里,便于测试。
- 增加 Wails 方法后必须运行 `wails generate module`,CI 会检查 `frontend/wailsjs` 是否最新。

## 10. 测试策略

单测(不依赖网络与真实显示器):

- 版本比较:带/不带 `v`、预发布、非法输入。
- `SHA256SUMS` 解析:正常、缺条目、重复条目、畸形行。
- asset 选择:按平台/产物类型选对文件。
- zip 解包:正常、路径穿越、绝对路径、符号链接、多顶层目录。
- 替换失败回滚时序:用临时目录模拟,断言原文件在失败后仍可用。
- 节流逻辑:时间注入,验证 24h 窗口。
- CLI 退出码与 `--check/--yes/非 TTY` 行为。

网络与 GitHub API 用接口注入假实现;平台替换逻辑在 macOS 与 Windows 的 CI 上跑临时目录测试,真机路径留在验收矩阵里人工验证。

## 11. 验收矩阵

### macOS GUI

1. 正常路径:装 v0.2.0 → 提示 v0.3.0 → 更新 → 重启 → footer 版本变化,标签/设置保留。
2. 从挂载的 dmg 直接运行 → 提示拖入 Applications,不尝试替换。
3. `/Applications` 不可写 → 提示无权限 + 打开下载页。
4. 下载中断 / SHA256 不符 / zip 版本与 tag 不符 → 原版本完好。
5. 替换到一半失败 → 自动恢复原版本。
6. 断网启动 → 无任何提示。

### Windows GUI

1. 正常路径:exe 位于用户目录 → 更新 → 立即重启 → 版本变化。
2. 运行中改名让位成功;`.old` 在新进程启动后仍存在,24h 后才清。
3. exe 所在目录不可写 → 降级下载页。
4. 更新到一半失败 → 原 exe 恢复可用。

### CLI

1. `upgrade` 交互确认、`--yes`、`--check` 三种退出码行为正确。
2. `dev` 构建:明确报"开发版不检查更新"。
3. Windows 上 `monctl upgrade` 后立即 `monctl version` 显示新版本。
4. 只读目录:明确报错,不弹 UAC。

### Release / CI

1. release 恰好 5 个产物 + `SHA256SUMS`。
2. `SHA256SUMS` 覆盖全部 5 个产物且与实际文件一致。
3. zip 解压后 `monctl.app` 的 `CFBundleShortVersionString` 等于 tag。
4. CI 运行 `internal/update` 的单测(版本比较、清单解析、解压防护、回滚时序)。
